# ADR-0010: A batch instance outlives its rowid

## Status

Proposed by issue #255.

## The decision this change introduces

`planned_batch.id` remains the compact integer parent key used by
`batch_occurrence`, but it is no longer enough to authorize an update or
delete. Every planned batch also gets one immutable random `instance_key`.
Every mutation must match the numeric id, household id, and instance key.

The key identifies one concrete lifetime of a batch. It is not an edit
revision: two simultaneous edits to the same live batch still use the existing
last-writer-wins behavior. It only prevents an action prepared for a deleted
batch from following a reused SQLite rowid onto a newly created batch.

## Why not `AUTOINCREMENT`

Changing the existing primary key to `AUTOINCREMENT` would require rebuilding
`planned_batch`. That table is the parent of `batch_occurrence` with `ON DELETE
CASCADE`, and D1 cannot use the ordinary transactional SQLite rebuild recipe
safely here. An additive column preserves every id, occurrence, and foreign
key.

Existing rows receive distinct random keys in the migration. New keys are
generated by the application, while database triggers reject missing keys and
later key changes. A unique index rejects collisions.

## Mutation boundary

The occurrence replacement transaction repeats all three identity checks in
its DELETE and every INSERT. Past-only editing may omit the recipe-readability
check, as ADR-0009 requires for historical records, but it never omits
household or batch-instance identity.

Screen forms carry the key they were rendered with. JSON clients receive it
when creating or listing a batch and must return it on PATCH or DELETE. Losing
the batch or its key produces the existing not-found shape; losing future
recipe access produces the existing controlled refusal, with the old
occurrences left intact.
